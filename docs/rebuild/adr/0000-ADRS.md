## ADR-001: Artifact / Example / Control Model

**Status:** Proposed
**Deciders:** Surface Rebuild spec author, Phase 2 review

### Context

The Playground and Docs engine both need to present interactive examples. Today, the docs package has facet-specific gallery code (F1) and the playground has a cosmetic "Device" select (F11). Neither can present arbitrary artifacts generically. A shared model is needed that:
- Lets any package contribute artifacts (components, layouts, motion effects, tokens, flows, auth lifecycles)
- Infers control panels from TypeScript props (avoiding 113 hand-authored panels)
- Generates code from control values
- Encodes URL state for shareable permalinks
- Is framework-agnostic at the core

### Decision

Adopt the Artifact/Example/Control model from spec §5.2–5.3. Three core types, registered via a kind registry:

```ts
type ViewportSpec = {
  fit: "content" | "frame";
  aspect?: "16:9" | "4:3" | "1:1" | "9:16" | number;
  minHeight?: number;
  resizable?: boolean;
  scroll: "none" | "inside";
};

interface ArtifactKind<TValues = Record<string, unknown>> {
  id: string;
  label: string;
  defaultViewport: ViewportSpec;
  render(artifact: Artifact, values: TValues, ctx: RenderContext): unknown;
  inferControls?(artifact: Artifact): ControlSchema;
}

interface Artifact {
  id: string;
  kind: string;
  title: string;
  package: string;
  summary?: string;
  viewport?: Partial<ViewportSpec>;
  examples: ExampleRef[];
}

interface Example<P = Record<string, unknown>> {
  id: string;
  artifact: string;
  title: string;
  description?: string;
  render: (props: P) => ReactNode;
  defaults?: Partial<P>;
  controls?: ControlOverrides<P>;
  code?: (props: P) => string;
  tags?: string[];
}
```

Control inference is tiered (spec §5.3):
1. **Inferred** from TS props at registry build (TS compiler API: union literals → select, boolean → switch, string → text, number → number, ReactNode → slot preset)
2. **Overridden** in the example (`controls:` field)
3. **Slot presets** — named alternatives defined in the example

Code view: `toCode()` (prop-diff against defaults → JSX) in `sandbox/core`.

### Consequences

- **Positive:** One model serves Playground, Docs embeds, and consumer docs. No per-component bespoke inspector. Generated code view. Shareable permalinks.
- **Negative:** TS compiler-based inference adds build-time complexity. Unsupported prop types are omitted (mitigation: overrides exist).

### Alternatives

| Alternative | Rejected |
|---|---|
| Hand-author 113 control panels | Would reintroduce the duplication the spec eliminates (F1). |
| Store examples as strings (not functions) | Loses type safety and editor support. Breaks refactor safety. |
| Free-form JSX editing only (no controls) | No tier-1 inference; forces users into code for every tweak. |
| Use Storybook's CSF (Component Story Format) | Requires full Storybook infrastructure + bundler plugins in every consumer. Overkill for a docs/playground split. |

## ADR-002: Sandbox v3 — Core / React / Live Split

**Status:** Proposed
**Deciders:** Surface Rebuild spec author, Phase 2 review

### Context

`@fusorb/facet-sandbox` v2 has:
- An unused block registry (`registerSandboxBlock`/`getSandboxBlock`/`listSandboxBlocks`) with zero external callers (F6).
- An unused adapter registry (`registerAdapter`/`getAdapter`/`listAdapters`) with zero external callers (F6).
- A parser in `react/index.tsx` that duplicates the docs engine's `LiveCodePlayground.tsx` parser (F7).
- The only consumer: one tab in `apps/playground`.

The real value is the no-`eval` JSX interpreter + URL sanitizer + error boundary + stage/inspector concept. These should be reusable by docs AND consumers.

### Decision

Rework to v3 with three subpaths. **No `@fusorb/*` runtime dependencies** (L1):

| Subpath | Contents | Deps |
|---|---|---|
| `/core` | Types + pure functions: `Artifact`, `Example`, `ControlSchema`, `Viewport`, kind registry (`registerArtifactKind`), control inference helpers, `toCode`, URL-state encode/decode | none |
| `/react` | `Stage` (bounded viewport host), `ArtifactRenderer`, `Inspector` (schema-driven, injectable control renderers), `Catalog`, `CodeView` | react (peer) |
| `/live` | No-`eval` JSX interpreter, `isSafeUrl`/`sanitizeUrlProps`, `PlaygroundErrorBoundary`, `PreviewFrame`, optional prettier formatting | react (peer, optional prettier) |

Breaking changes: remove `registerSandboxBlock`/`getSandboxBlock`/`listSandboxBlocks`/`registerAdapter`/`getAdapter`/`listAdapters`/`reactAdapter`/`Sandbox`/`SandboxProvider`/`useSandbox` from the main barrel. The live-JSX runtime moves to `/live`.

The `Inspector` accepts **injectable control renderers** — facet-styled in `apps/playground`, consumer-styled in consumer apps. The kit must be usable with zero facet components (composability test).

### Consequences

- **Positive:** Single copy of parser/sanitizer. Reusable lab kit for docs + consumers. Framework-agnostic core. Zero facet deps.
- **Negative:** Breaking change — major version bump (2.0 → 3.0). Removing unused API. Need codemod note (no known external consumers to verify via npm).

### Alternatives

| Alternative | Rejected |
|---|---|
| Delete sandbox entirely | The interpreter, sanitizer, stage, and inspector are genuinely reusable. Deleting would lose the asset. |
| Create new `facet-lab` package | Adds a package for no gain; name/home already exist as `@fusorb/facet-sandbox`. |
| Keep v2 as-is, copy parser into docs | Two copies of security-sensitive sanitizer will drift (F7). Violates DRY + L1. |

## ADR-003: Docs Engine Split + DocsDataSource + Router Seam

**Status:** Proposed
**Deciders:** Surface Rebuild spec author, Phase 2 review

### Context

`@fusorb/facet-docs` currently ships facet's own gallery (F1), hard-depends on auth + sdk (F2), hard-wires `BrowserRouter` (F3), and hard-codes facet vocabulary (F4). A consumer who installs `@fusorb/facet-docs` gets facet's catalog baked in.

### Decision

1. **Split facet-specific code out of the package.** `lib/variants.tsx` (4,285 lines), `lib/usage.ts` (3,162 lines), `components/previews.tsx` (1,813 lines), `components/playground-registry.tsx`, `components/AuthDemo.tsx`, `components/AuthPreviews.tsx`, `components/LayoutPreviews.tsx`, `components/ReadyToUseDemos.tsx`, `components/Playground.tsx`, `components/PlaygroundPage.tsx`, `components/InteractiveDemo.tsx`, `components/ComponentDemoCard.tsx`, `lib/manifest.ts` (extendedEntries), `lib/nav.tsx` (ORDER, buildComponentsSection), `pages/{Component,Components,Pages,ReadyToUse}Page.tsx`, `docs-app.test.tsx` — all move to apps/docs as registry-driven code or are deleted.

2. **`DocsDataSource` seam:**
```ts
interface DocsDataSource {
  entries(): ReferenceEntry[];
  examples(slug: string): Example[];
  api?(slug: string): ApiDoc | undefined;
}
```
A consumer without a gallery passes none. Facet passes registry-backed data.

3. **Router seam:**
```ts
interface DocsAppProps {
  config: DocsConfig;
  dataSource?: DocsDataSource;
  routerKind?: "browser" | "hash";  // DocsApp: batteries (owns router)
  router?: RouterAdapter;            // DocsRoutes: router-less, host injects
  // DocsRoutes: mount inside any host router
}
```
`DocsApp` (batteries) and `DocsRoutes` (router-less) — both accept a `RouterAdapter` (reuse layout's concept).

4. **Sections config (not constants):**
```ts
interface DocsConfig {
  sections: { id: string; label: string; order: number; icon?: string }[];
  brand: { name: string; url: string; github: string; ... };
}
```

5. **`DocsPage.load?: () => Promise<DocsBlock[]>`** — code-split per page for scale.

6. **Live code delegates to `@fusorb/facet-sandbox/live`.**

### Consequences

- **Positive:** Consumers install a docs shell without auth/sdk. Component gallery is data-driven, not baked in. Router-injectable.
- **Negative:** Major version bump (1.5 → 2.0). Breaking API changes to DocsApp, sections, exports. `check:docs` rewired to read registry, not manifest.ts.

### Alternatives

| Alternative | Rejected |
|---|---|
| Leave facet gallery in the package | Fails L3 (engines are facet-agnostic). Consumers get facet's catalog baked in. |
| Keep `BrowserRouter` hard-wired | Cannot embed in a host that owns routing (e.g., Next.js apps). Layout already solved this with RouterAdapter. |
| Adopt MDX | Requires a bundler plugin in every consumer. Cannot be serialized. Cannot be indexed by search/Intel without executing code. (L4/D-4) |

## ADR-004: Layout / Auth Decoupling via Session Seam

**Status:** Proposed
**Deciders:** Surface Rebuild spec author, Phase 2 review

### Context

`@fusorb/facet-layout` hard-depends on `@fusorb/facet-auth` (F5): four source files (`console-layout.tsx`, `chat-layout.tsx`, `user-menu.tsx`, `sidebar-auth.tsx`) import `useOptionalAuth`. A consumer wanting only an app shell receives auth + sdk + zod + react-hook-form. The hook is *optional* by name, so the coupling should be an injected seam, not a dependency (L1/L2).

### Decision

1. **Remove the `auth` dependency from `layout`.** Replace all `useOptionalAuth` imports with an injectable `session` seam on `LayoutProvider`:
```ts
interface LayoutProviderProps {
  config: LayoutConfig;
  session?: { user: User; signOut: () => void };
  router?: RouterAdapter;
  children: ReactNode;
}
```
2. **`@fusorb/facet-auth` becomes an optional peer** of `layout`. A documented `useAuthSession()` helper is exported from **auth** (not layout), so consumers wire auth → layout explicitly:
```tsx
// In app:
const { session } = useAuthSession();
<LayoutProvider config={config} session={session} router={adapter}>
  ...
</LayoutProvider>
```
3. **Add `LayoutSkeleton` as `./skeleton` subpath** — pure presentational, no providers, usable as Suspense fallback (L2). Skeleton kinds/options derived from real layout prop types (validated by `check:layout-skeleton-parity`).
4. **Add `data-region` attributes** to real shells (`sidebar`, `header`, `aside`, `content`, etc.) for skeleton parity testing.

### Consequences

- **Positive:** Layout ships without auth/sdk/zod/react-hook-form. Consumers decide auth integration. Skeleton usable as standalone loading fallback.
- **Negative:** Breaking change if `useOptionalAuth` was part of layout's public API (checking: it's imported FROM auth INTO layout — the seam goes the other direction, so this is an internal change + one optional-peer addition = minor version, not major, unless public export types change). Decision: minor bump if no public prop changes, major if `LayoutProvider` props change. ADR will defer to Phase 3 implementation.

### Alternatives

| Alternative | Rejected |
|---|---|
| Keep the auth dependency in layout | Fails L1 (composability first). "Optional" by name but hard by install. |
| Delete useOptionalAuth entirely | Breaks existing consumers who rely on it. |
| Move skeleton to playground app | Violates L2 (apps own no capability) and introduces drift. |

## ADR-005: Docs Content Format — Markdown + Directives

**Status:** Proposed
**Deciders:** Surface Rebuild spec author, Phase 2 review

### Context

Docs prose is currently hand-typed as `DocsPage[]` in `apps/docs/src/pages.ts` (1,845 lines). This is unreviewable, unmergeable, and unchunkable. The engine needs authored narrative + generated reference + generated examples, with cross-reference validation.

### Decision

Author prose in **Markdown files with frontmatter + directive syntax**, compiled at build time into the existing `DocsBlock[]` model. **No MDX** (needs bundler plugin in every consumer; not serializable; not indexable by search/Intel without executing code).

```md
---
title: Theming
section: foundations
order: 20
summary: How tokens, presets and themes compose.
---

Facet ships {{facts.components.count}} components across {{facts.packages.count}} packages.

::example{id="theme-provider.basic"}

:::callout{tone="note"}
Presets change behaviour, not just colour.
:::

::reference{kind="package" id="@fusorb/facet-motion"}
```

Directive → block type mapping:
- `::example` → `demo` or `example` block (interactive, with "open in playground")
- `::install` → `install` block (generated install command from registry)
- `::reference` → `table` block (generated API/props from registry)
- `::callout` → `callout` block (info/warning/note)

Build **fails** on: unknown example id, unknown registry reference, unresolved `{{facts.*}}`, broken internal link, duplicate page paths, missing frontmatter.

### Consequences

- **Positive:** Author-friendly (any markdown editor), git-friendly (reviewable diffs), build-time validation, per-page code-splitting via `DocsPage.load`, works for consumers without a registry.
- **Negative:** Need a content compiler (Phase 3). Directive parsing adds complexity. Consumers must run `facet docs build`.

### Alternatives

| Alternative | Rejected |
|---|---|
| Keep pages.ts as TS literals | Hostile to authors and scale. Facet already shows early symptoms (4,285 + 3,162 + 1,813 line files). |
| Adopt MDX | L4/D-4: needs bundler plugin, not serializable, not indexable. |
| Single giant file (50k–100k lines) | Loads as "just text" but fails for workflow and scale: unreviewable diffs, merge conflicts, no per-page split, slow editor/TS server. |
| One tiny file per component | Fragments for no gain. |

**Rule (spec §6.2):** Authored narrative = one `.md` per topic/page. Reference = generated, zero files. Compiled output = one lazy chunk per page + small search index.

## ADR-006: Registry Schema + Package `facet` Metadata

**Status:** Proposed
**Deciders:** Surface Rebuild spec author, Phase 2 review

### Context

Editorial metadata (package order, icons, categories) is scattered across generator scripts (F9): `PACKAGE_ORDER`/`PACKAGE_ICONS` in `gen-site-data.mjs`, `CATEGORY` in `gen-docs-manifest.mjs`. Adding a package requires editing scripts. Facts are hand-typed and disagree (F8).

### Decision

1. **Package metadata in `package.json`:**
```json
{
  "name": "@fusorb/facet-components",
  "facet": {
    "category": "components",
    "icon": "component",
    "order": 5,
    "summary": "112 styled UI components built on Radix primitives"
  }
}
```
New package = appears everywhere automatically. `category` ∈ `"foundation" | "primitives" | "components" | "data" | "ui" | "tooling" | "app"`.

2. **Component metadata in source:** JSDoc `@category` and `@summary` on exported components (replaces `CATEGORY` map). 14/112 components already have partial JSDoc (`@example` only); Phase 5 adds comprehensive tags.

3. **Registry output** (`registry.json`, versioned `schemaVersion: 1`):
```ts
interface FacetRegistry {
  schemaVersion: 1;
  generatedFrom: { commit: string; at: string };
  packages: PackageEntry[];
  components: ComponentEntry[];   // slug, name, package, category, summary, props[], examples[]
  layouts: LayoutEntry[];          // kind, props, modes, regions[], presets[]
  motion: { families: ...; authored: ...; domains: ... };
  tokens: { groups: ...; vars: ... };
  presets: PresetEntry[];          // domain presets
  examples: ExampleEntry[];
  facts: Record<string, string | number>;  // {{facts.*}} interpolation source
  surfaces: SurfaceMap;            // canonical URLs/routes
}
```

4. **Facts are derivation-defined, not hand-typed:** `components.count` = number of non-test `.tsx` exports. `tests.count` is NOT a committed fact — docs MAY show it only as a CI-injected value, or not at all (F8).

### Consequences

- **Positive:** One source of truth per fact (L4). Adding a package/component updates everything. Generated README/changelog regions. No script edits for new packages.
- **Negative:** Need to backfill `facet` metadata into all 13 package.json files. Need to migrate `gen-site-data.mjs` and `gen-docs-manifest.mjs` to read from the registry.

### Alternatives

| Alternative | Rejected |
|---|---|
| Keep metadata in scripts | F9: fragile, requires script edits, no single source of truth. |
| TS-only registry (no JSON) | Not readable by Intel or other non-TS tooling. |
| Generate into each app | Re-creates drift (multiple generated copies). |
| Publish the registry | Premature API surface; the spec requires it be private workspace-only. |

## ADR-007: Surface Config (URLs, Domains, Viewports, Themes)

**Status:** Proposed
**Deciders:** Surface Rebuild spec author, Phase 2 review

### Context

URLs and tokens leak into apps (F10): `localhost:5173`, `facet.so/docs`, `facet.so/playground`, GitHub URLs, npm URLs, Google Fonts URLs are hard-coded across `apps/landing/src/site.config.ts`, `apps/playground/src/App.tsx`, `apps/docs/src/app.tsx`. Visual literals (colors, fonts, z-index) are also hard-coded in app CSS/HTML (L6).

### Decision

Single source of truth for cross-surface configuration:

```ts
interface SurfaceConfig {
  surfaces: {
    landing: { originDev: "http://localhost:5173"; originProd: "https://facet.so" },
    playground: { originDev: "http://localhost:5175"; originProd: "https://facet.so/playground" },
    docs: { originDev: "http://localhost:5174"; originProd: "https://facet.so/docs" },
  };
  github: string;            // "https://github.com/fusorb/facet"
  npmScope: string;          // "@fusorb"
  domains: PresetEntry[];    // fintech, med, edu, enterprise, default
  viewports: ViewportPreset[]; // desktop, tablet, mobile, 16:9, 4:3, 1:1, 9:16
  themes: { light: string; dark: string };
}
```

- `surfaces.config.ts` lives in the root (workspace-level, consumed by all apps).
- Dev/prod values by environment variable or build flag.
- Apps expose permalink helpers (no app writes another app's URL by hand).
- Visual literals (fonts, colors, z-index, spacing) come from `@fusorb/facet-tokens` or the Tailwind theme — NOT from app CSS.
- Google Fonts → `tokens` package CSS (loaded via the tokens barrel, not per-app `@import url()`).

### Consequences

- **Positive:** One place to change origins, domains, viewports. Apps can't diverge. Lint gate (`check:surfaces`) catches violations.
- **Negative:** Need to migrate all existing hard-coded URLs. Google Fonts must move to tokens (or be self-hosted).

### Alternatives

| Alternative | Rejected |
|---|---|
| Per-app config files | Creates drift (F10). Same origin defined 3× as 3 different strings. |
| Environment variable per variable | Too many env vars. No typed schema. |
| Keep URLs in apps | The entire point of F10 is that this is wrong. |
