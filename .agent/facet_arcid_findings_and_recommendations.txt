2. CONFIRMED CRITICAL ISSUE — TOKEN STORAGE (BOTH REPOS)
----------------------------------------------------------------------------
This is no longer a suspected risk — it's confirmed in running code on both
sides:

  facet: packages/auth/src/storage.ts — `defaultStorage` writes
  accessToken/refreshToken straight to window.localStorage under
  "arcid_access_token" / "arcid_refresh_token". No secure default shipped.

  arc-id: src/sdk/index.ts — `persistSession()` writes the FULL session
  (user object + accessToken + refreshToken) to plain
  localStorage.setItem("arcid-auth", ...). src/providers/auth-provider.tsx
  reads it back on every mount via localStorage.getItem("arcid-auth").

  This means arc-id built its OWN persistence layer on top of facet's
  (bypassing facet-auth's defaultStorage and facet-store's
  createZustandTokenStorage bridge, which only handles in-memory
  refresh — it does NOT persist to disk itself). The actual disk
  persistence is arc-id's custom AUTH_STORAGE_KEY logic, and it's the
  least safe part of the whole chain: any XSS on any page (npm supply
  chain compromise, dependency vuln, injected script) can read
  localStorage and exfiltrate a live session + refresh token with zero
  additional exploitation needed.

  This is not a facet problem that arc-id inherited passively — arc-id
  wrote net-new code that reintroduces the exact risk facet's own default
  already carries. Fixing facet's default alone will NOT fix arc-id unless
  arc-id's persistSession/clearPersistedSession is also rewritten.

  RECOMMENDED FIX (both repos, in order):
  a. arc-id backend: add an httpOnly, Secure, SameSite=Strict cookie path
     for the refresh token (the API already depends on @fastify/cookie —
     it's installed but apparently not used for this purpose yet based on
     the flows inspected). Access token can stay in memory (Zustand,
     non-persisted) and be silently re-minted from the httpOnly refresh
     cookie on page load via a /oauth/token refresh call — this removes
     the need to ever put a refresh token in localStorage or JS-reachable
     state at all.
  b. arc-id frontend: delete persistSession/clearPersistedSession's
     localStorage writes for the refresh token entirely. The access token,
     if kept in localStorage for convenience, is a materially smaller risk
     than the refresh token (short TTL, revocable) — but the ideal end
     state is access token in memory only, rehydrated on mount via the
     cookie-backed refresh call.
  c. facet/packages/auth/src/storage.ts: change `defaultStorage` to require
     an explicit opt-in for localStorage (e.g. rename to
     `localStorageStorage` and export it, but make `ArcProvider` require a
     `storage` prop or throw a clear dev-time warning if none is passed).
     This stops the CLI-scaffolded starter apps for ArcWallet-adjacent
     products (ArcVerify, ArcIssuer, ArcKYC, ArcHealth, ArcEdu, ArcBase)
     from silently inheriting the same vulnerability the moment they run
     `facet install auth`.
  d. facet/packages/store: `createZustandTokenStorage` should gain an
     optional `persist` adapter argument so consumers can plug in a
     cookie-backed refresh call instead of (or in addition to) in-memory
     state, making the secure pattern the path of least resistance rather
     than something arc-id has to hand-roll.

  Severity: HIGH. This should be the next priority item in both repos
  before any of the polish items below.


3. DOC-DRIFT / STALE CLAIMS FOUND
----------------------------------------------------------------------------
- arc-id CLAUDE.md states: "arc-id keeps its indigo primary via override."
  This does NOT match the current source. src/styles/globals.css has no
  --primary override — it fully imports @fusorb/facet-tokens/tailwind.css
  and only overrides font-family fallback stacks. facet-tokens' own Alpha
  Palette already resolves --primary to Electric Cyan (#4AD3F5), so the
  design system migration for color appears DONE, not pending as the doc
  claims. Confirm visually in the running app and correct the doc — this
  is a documentation accuracy problem, not a code problem, but it's the
  exact kind of drift that misled the last review.

- facet's own CSS still ships a utility class named `.glow-indigo` (in
  packages/tokens/src/tokens.css and used throughout
  packages/components/src/ui/*.tsx and packages/layout). The class itself
  correctly resolves through var(--primary) (i.e., it actually renders
  cyan, not indigo) — but the NAME is a leftover from before the Alpha
  Palette rebrand. This is purely cosmetic (a naming/readability issue for
  any developer reading the component source), but it's worth a rename
  changeset (`glow-indigo` → `glow-primary` or `glow-accent`) since it
  actively misleads anyone reading facet's own source, including future
  AI agents working on the repo.

- arc-id's transactional email palette (src/core/mail/brand.ts,
  MAIL_COLOR.primary = "#000000") is a THIRD, independent palette — not
  indigo, not Electric Cyan, but black/white minimalist. This may be an
  intentional email-specific design choice (dark accents render more
  reliably across email clients than glassmorphic cyan), but it means
  arc-id currently ships three different "primary" brand colors depending
  on surface (web app = Electric Cyan via facet-tokens, docs claim =
  indigo (stale), email = black). Worth an explicit decision, not an
  accident.

5. TAILWIND — CORRECTION FROM PRIOR REVIEW
----------------------------------------------------------------------------
You're right, and the prior review's suggestion #3 ("ship a
tailwind.config preset") was wrong for this stack. Confirmed in
arc-id/postcss.config.mjs and facet/packages/tokens: this is Tailwind v4,
which is CSS-first and has no tailwind.config.* file at all — configuration
happens via @theme/@source directives directly in CSS (already done
correctly in both repos: facet-tokens/src/tailwind.css defines the
@theme mapping, and arc-id/src/styles/globals.css correctly uses @source
to point Tailwind's scanner at the published facet package dist folders,
since v4 doesn't scan node_modules by default).

The ACTUAL open gap here (correctly identified in facet's own CLAUDE.md,
independently confirmed) is narrower than "missing config file":
consuming apps have to manually remember to write those @source lines
for every facet package they use, and there's no CLI step that does this
automatically. `facet docs init` / `facet install` could emit or verify
these @source lines as part of scaffolding, so a new consumer (ArcVerify,
ArcKYC, etc.) doesn't discover "my facet components are rendering
unstyled" the hard way, the same way arc-id apparently did (see the long
explanatory comment already in arc-id's own globals.css about exactly
this gotcha).

RECOMMENDATION: add a `facet doctor` or `facet check:tailwind` command
that scans the consumer's globals.css/app.css for the required @source
lines per installed facet package and fails/fixes if missing. Low effort,
directly prevents the most common "why is nothing styled" support
question.


6. THE REAL STRUCTURAL GAP: REACT NATIVE / ARCWALLET
----------------------------------------------------------------------------
This is the most consequential finding from cross-referencing both repos
against your stated ecosystem plan (ArcWallet on React Native/Expo).

Confirmed by direct inspection of facet's own docs content and package
descriptions:
  - @fusorb/facet-store: explicitly "web + React Native" — pure Zustand,
    no React DOM dependency. Works today in RN.
  - @fusorb/facet-sdk: explicitly framework-agnostic (fetch-based, zero
    React) — works today in RN.
  - @fusorb/facet-tokens: "framework-agnostic" is claimed, but in practice
    it ships as CSS custom properties (tokens.css/tailwind.css). CSS
    variables do not exist in React Native's styling model — RN needs the
    actual hex/oklch VALUES as a JS object, not a stylesheet. The Alpha
    Palette object (packages/tokens/src/colors.ts) IS plain TS constants,
    so this part is technically reusable, but nothing currently packages
    it as an RN-consumable theme (e.g. a NativeWind config or a plain JS
    theme object with the same token names as the CSS variables).
  - @fusorb/facet-components, @fusorb/facet-auth, @fusorb/facet-layout:
    all built on Radix UI primitives + DOM elements + Tailwind classNames.
    None of this renders in React Native. There is currently no RN
    equivalent of Button, Card, SignIn, ConsoleLayout, etc.

Net effect: when ArcWallet development starts, facet in its current form
gives it a working SDK and state layer, but ZERO reusable UI — every
screen, form, and the entire SignIn/MFA/passkey flow UI would have to be
rebuilt from scratch in RN, duplicating exactly the kind of effort facet
was created to eliminate ("replace ~100 duplicated shadcn components
between projects" — the same duplication risk now exists across the
web/native boundary instead of across web projects).

RECOMMENDATION: before ArcWallet UI work starts, decide the RN strategy
explicitly rather than discovering it mid-build:
  Option A (lower effort, lower fidelity): NativeWind + a hand-ported
    subset of the highest-value components (Button, Input, Card, the auth
    forms) styled from the same Alpha Palette token values. Keeps design
    consistency; doesn't reuse facet-components code directly.
  Option B (higher effort, higher payoff): a facet-native package
    (@fusorb/facet-native) mirroring facet-components' primitive layer
    using RN-compatible primitives (React Native Paper, Tamagui, or
    Gluestack as the underlying primitive layer instead of Radix), wired
    to the same Alpha Palette tokens and the same facet-auth state
    machine/config shape (fintech/med/edu presets), so SignIn's
    IDLE→SELECT_METHOD→...→COMPLETE state machine and domain presets are
    shared logic even though rendering differs.
  Given ArcWallet's role as the TOTP authenticator (per earlier
  architecture decisions) and that it will need passkey-adjacent and
  MFA UI, Option B is the better long-term investment if more than
  ArcWallet alone will need mobile UI (ArcKYC document capture and
  ArcHealth likely will too, per the ecosystem list).
