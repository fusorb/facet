ARCEVOCIRQLE — FACET/ARCID ROADMAP
Sequencing: security fixes → stable publish → facet v1.x growth (driven by
arc-id) → facet v2 mobile strategy → ArcWallet kickoff on a ready kit.
Companion document to: facet_arcid_findings_and_recommendations.txt
============================================================================

RATIONALE FOR THIS ORDER
----------------------------------------------------------------------------
Building the React Native kit or any "future ArcWallet" component before
arc-id has actually needed and used the underlying primitive means
designing UI blind, against a guessed API shape instead of a proven one.
Every component in the gap list below except the RN kit itself is
something arc-id's own console pages will want on their own timeline,
independent of ArcWallet. Let arc-id's real usage prove the design first;
port proven components to mobile second. This also matters more than usual
here because both repos are maintained by one person — sequencing wrong
means paying a full context-switch cost twice instead of once.


PHASE 0 — STOP THE BLEEDING (do first, blocking everything else)
----------------------------------------------------------------------------
Scope: the items marked P0/P1 in facet_arcid_findings_and_recommendations.txt.

1. Fix token storage in both repos:
   - arc-id: move refresh token off localStorage onto an httpOnly/Secure/
     SameSite cookie; keep access token in memory only, rehydrated on
     mount via a cookie-backed refresh call. Retire persistSession's raw
     localStorage write of the full session object.
   - facet/packages/auth/storage.ts: stop defaulting silently to
     localStorage; require an explicit storage choice or emit a clear
     dev-time warning.
   - facet/packages/store: add an optional persist adapter to
     createZustandTokenStorage so the cookie-backed pattern is the easy
     path for every future consumer (ArcVerify, ArcIssuer, ArcKYC,
     ArcHealth, ArcEdu, ArcBase), not just something arc-id has to
     hand-roll again.

2. Publish facet's stabilization backlog to npm:
   - @fusorb/facet-cli 1.0.0 (currently 0.8.0 on npm)
   - @fusorb/facet-store 1.0.0 (currently 0.1.0 on npm) — do this in the
     same pass as the token-storage fix, since the fix touches this
     package directly.

3. Bump arc-id's package.json pins to the newly published versions.

4. Doc cleanup: correct arc-id/CLAUDE.md's stale "indigo primary via
   override" claim; rename facet's `.glow-indigo` utility class to
   something palette-accurate; make an explicit decision on the
   three-palette situation (web = Electric Cyan via facet-tokens, docs
   claim = stale indigo, email = black/white) instead of leaving it as
   drift.

Exit criteria: no session data in raw localStorage anywhere in arc-id;
facet-cli and facet-store both at 1.0.0 on npm and in arc-id's
package.json; no stale color claims in either repo's docs.


PHASE 1 — FACET v1.x GROWS WITH ARC-ID (ongoing, not a separate sprint)
----------------------------------------------------------------------------
These ship into the current facet v1.x line as arc-id's console actually
needs them — no version-2 branch, no mobile decision required yet. Each
one should be written headless-first: state/validation/gating logic
separated from the Radix/DOM rendering layer, so it can be re-rendered for
React Native later without redesigning the logic.

1. Stepper / wizard primitive
   - Generic <Stepper> with per-step validation gating, back/forward,
     and progress indicator variants (dots, numbered, labeled).
   - Pairs with facet's existing form.tsx (react-hook-form + zod).
   - Immediate arc-id use: tenant onboarding, KYC-adjacent flows,
     multi-step credential issuance.
   - Headless split: a useStepper() hook (current step, canGoNext,
     validation state) separate from <Stepper> rendering, so a future
     RN <Stepper> can reuse the hook unchanged.

2. Charts / usage visualizations
   - Line/bar chart wrapper themed to the Alpha Palette (Recharts is a
     reasonable default choice given the existing stack).
   - Immediate arc-id use: billing usage trends on billing-page, audit
     log activity over time paired with the existing activity-feed.tsx.
   - Lower priority for headless-splitting — charting logic is generally
     rendering-library-specific either way (Recharts on web, Victory
     Native or similar on RN), so this one is more "redesign later" than
     "port later," and that's fine.

3. Consent / e-signature capture
   - Scrollable document viewer with "must scroll to accept" gating,
     plus a typed-name or drawn-signature capture widget.
   - Wires directly into arc-id's existing backend gate:
     TenantPolicy.requireLegalConsent + the legalConsent table already
     enforced in issue-credential.flow.ts. This is a real, currently
     unmet frontend need, not a speculative one.
   - Headless split: a useConsentGate() hook (has-scrolled-to-bottom,
     has-signed state) separate from the document viewer/signature pad
     rendering.

4. Browser-based QR / barcode scanner (web version)
   - getUserMedia-based scanner component, distinct from the existing
     qrcode.tsx generator.
   - Immediate arc-id/ArcVerify use case: verifying credentials via a
     laptop/desktop webcam before any native ArcVerify app exists.
   - This is explicitly the WEB half of item 2 in Phase 3's mobile list
     below — build it now for browser use; the native camera version is
     a separate, later effort once the RN kit exists.

Exit criteria: each of the four items ships as a normal facet-components
changeset, consumed by at least one real arc-id console page (not just
built speculatively), with headless logic separated from rendering.


PHASE 2 — DECIDE THE REACT NATIVE STRATEGY (a decision, not a build)
----------------------------------------------------------------------------
Do this once Phase 1 is far enough along that you have 2-3 headless
hooks already proven (useStepper, useConsentGate at minimum), and before
committing calendar time to Phase 3.

Decision: NativeWind-port vs. a real @fusorb/facet-native package.

  Option A — NativeWind + hand-ported subset
    Lower effort, lower fidelity. Port Button, Input, Card, and the core
    auth forms directly, styled from the Alpha Palette token values via
    NativeWind. Doesn't reuse facet-components code, just the design
    tokens and (if Phase 1 was done headless-first) the validation/state
    hooks.

  Option B — @fusorb/facet-native package
    Higher effort, higher payoff. Mirrors facet-components' primitive
    layer using an RN-compatible primitive library (React Native Paper,
    Tamagui, or Gluestack in place of Radix), wired to the same Alpha
    Palette tokens and the same facet-auth domain-preset shape
    (fintech/med/edu configs), so SignIn's state machine and the Phase 1
    headless hooks are shared logic across web and native, not
    reimplemented.

  Recommendation: lean toward Option B if ArcKYC or ArcHealth will also
  need mobile UI (both are named in the ecosystem list, and KYC document
  capture in particular is a mobile-native-feeling task — camera,
  guided framing, liveness check). If ArcWallet turns out to be the only
  mobile consumer for the foreseeable future, Option A is the pragmatic
  choice and can be upgraded to Option B later without much sunk cost,
  since the token values and headless hooks carry over either way.

Exit criteria: one paragraph committed to a planning doc (e.g.
docs/planning/ in facet or arc-id) stating which option was chosen and
why, so this doesn't get re-litigated mid-build.

DECISION — SETTLED (supersedes any "make everything headless / drop
Radix" idea raised during planning):

  facet-components keeps Radix. Do NOT attempt to strip Radix from the
  existing 93 components or make them "DOM-agnostic." Radix's value isn't
  its API surface — it's DOM-native interaction behavior (focus trapping
  via document.activeElement, dismissable-layer listeners on document,
  Popper-style positioning via getBoundingClientRect, portals via
  ReactDOM.createPortal). None of that exists in React Native; there is
  no DOM to be agnostic over. Removing Radix doesn't remove the DOM
  dependency, it just means hand-rolling an unmaintained, untested
  replacement for what Radix already solves — while gaining zero ground
  toward RN support, invalidating ~276 existing component tests, and
  destabilizing a library arc-id already fully depends on in production.

  Option B is the settled direction: @fusorb/facet-native as a genuinely
  separate package with its own RN-appropriate primitive layer (React
  Native Paper, Tamagui, or Gluestack — pick one during Phase 2 proper —
  in place of Radix), sharing only what's actually platform-agnostic:
  Alpha Palette token VALUES (not the CSS variables — RN needs a plain JS
  theme object; packages/tokens/src/colors.ts is already plain TS
  constants, so this is a repackage task, not new design work),
  facet-sdk, facet-store, and any headless state/validation hooks
  extracted during Phase 1 (useStepper, useConsentGate, etc.).

  Ongoing, low-risk, worth doing incrementally as existing components are
  touched anyway: extract genuinely DOM-independent state that already
  exists (e.g. Combobox's selected/open state, the validation logic
  already living in packages/auth/src/validators.ts) into shared hooks.
  This is NOT a blanket rewrite — just convenient overlap for
  facet-native later, done opportunistically, not as a dedicated sprint.


PHASE 3 — BUILD FACET v2 MOBILE KIT (before ArcWallet kickoff)
----------------------------------------------------------------------------
Scope depends on the Phase 2 decision. In either case, port in this order
of priority, based on what ArcWallet will need first as the TOTP
authenticator role:

1. Design tokens as a plain JS/TS theme object (Alpha Palette is already
   plain TS constants in packages/tokens/src/colors.ts — this is largely
   a re-export/repackage task, not new design work).
2. Auth primitives: Button, Input, Card, form field components — the
   smallest set needed to render SignIn/MFA screens.
3. SignIn/MFA state machine bindings — reuse facet-auth's existing
   IDLE→SELECT_METHOD→...→COMPLETE state machine and domain presets
   (fintech/med/edu/enterprise) as-is; only the rendering layer is new.
4. Native camera QR/barcode scanner — the native counterpart to Phase
   1's browser scanner, now justified by ArcVerify/ArcWallet's actual
   native use case.
5. Guided document capture flow (frame overlay, retake, blur/glare
   detection) + optional liveness check — for ArcKYC, if in scope for
   this phase; otherwise defer to a follow-up once ArcKYC development
   actually starts.

facet-store and facet-sdk need no work here — both are already
framework-agnostic and work in RN today.

Exit criteria: a minimal working RN screen (sign-in + MFA) rendered from
@fusorb/facet-native (or the NativeWind port) against a real Expo app,
before ArcWallet's own feature work begins on top of it.


PHASE 4 — ARCWALLET KICKOFF
----------------------------------------------------------------------------
ArcWallet development starts consuming a stable, already-proven mobile
kit instead of building UI and security patterns from scratch under
feature-delivery pressure. TOTP authenticator role work begins here.


PHASE X — PRODUCTION-GRADE / SYSTEM-INTEGRATION HARDENING FOR ARCID
----------------------------------------------------------------------------
Runs alongside Phase 0/1, not after — these are backend/API-contract
concerns independent of the facet UI work above, but load-bearing for
"arc-id as a platform other systems build against," which is the whole
point of ArcID being a standard-shaped OIDC/OAuth provider.

Verified already solid — do not rework, do not second-guess:
  - Webhook delivery: HMAC-SHA256 over `${timestamp}.${body}` (Stripe's
    scheme), timestamp-based replay protection, exponential backoff with
    jitter, distributed leasing via Postgres FOR UPDATE SKIP LOCKED,
    SSRF guard re-validated on every redirect hop (not just the initial
    URL). This is genuinely production-grade as-is.
  - client_credentials OAuth grant: fully implemented, tested, spec-
    correct (rejects openid/offline_access scopes appropriately for
    machine grants). This is the M2M auth story and it's done.
  - OpenAPI 3.1 spec is auto-generated from the live Zod route schemas
    via fastify-type-provider-zod — it cannot drift from the actual API
    surface, which is exactly the property you want before generating
    third-party client SDKs from it.
  - Rate limiting already keys by identity+tenant when authenticated,
    specifically to stop one noisy tenant from degrading another's
    quota — the mechanism is right; only the plan-tier policy layer on
    top is unfinished (see below, and this is already flagged in arc-id's
    own code comments as pending Phase F — not a fresh discovery).

Confirmed gaps, in priority order:

1. Idempotency-key enforcement — HIGH PRIORITY.
   `X-Idempotency-Key` is allowlisted in the CORS headers config but
   NOTHING reads, stores, or dedupes it anywhere in the codebase. Any
   integrating system that retries a timed-out mutating call (issue
   credential, create tenant, create OAuth client) today risks a
   duplicate side effect. Build: a small Fastify plugin/preHandler that,
   for POST/PUT/PATCH routes opting in, looks up the (tenantId, key)
   pair in a short-lived store (Redis, given it's already a dependency),
   and on a hit replays the original stored response instead of
   re-executing the flow. This is the single most consequential item for
   "perfectly integrable into systems" — do this before or alongside the
   API-key decision below, since it matters regardless of auth style.

2. API key management — ARCHITECTURAL DECISION, THEN BUILD.
   No ApiKey model exists in prisma/schema.prisma. Machine auth today is
   OAuth client_credentials only — correct and standards-aligned, but not
   what most external developers expect when they hear "API key" (no
   token-exchange round trip, just a static scoped bearer credential).
   Meanwhile facet already ships a fully-built api-key-manager.tsx UI
   component with nothing behind it in arc-id — this needs a decision,
   not a silent fix:
     a. Decide whether arc-id wants static, scoped API keys as an
        additional (not replacement) auth surface alongside
        client_credentials — likely yes, for the "quick server script /
        simple webhook consumer" integration case that client_credentials
        makes unnecessarily heavy.
     b. If yes: ApiKey model (hashed key storage, never store plaintext;
        scoped to a subset of RBAC permissions; per-key rate limit
        override; last-used-at tracking; rotation with a grace period so
        a rotated key doesn't break in-flight integrations instantly).
     c. Wire api-key-manager.tsx to the new backend, or explicitly
        decide to deprecate/hide it from default facet-auth installs
        until this is built, so new consumers (ArcVerify, ArcIssuer,
        etc.) don't render a UI for a feature that doesn't work.

3. Distributed tracing — MEDIUM PRIORITY, GROWS WITH ECOSYSTEM.
   Zero OpenTelemetry references confirmed. requestId is already threaded
   through flows and structured Pino logs, which is sufficient for
   single-service debugging today. As more Arc* services come online and
   start calling each other (ArcWallet → ArcID, ArcVerify → ArcID →
   ArcIssuer, etc.), trace propagation across service boundaries becomes
   necessary to debug cross-service latency/failures. Not urgent while
   arc-id is the only running service; revisit once a second service is
   actually live and calling it.

4. Per-tenant plan-tier rate limiting — already tracked internally as
   Phase F in arc-id's own comments; the mechanism (identity+tenant
   keying) is done, only the plan-based quota policy layer is pending.
   No new discovery here, just confirming it's real and already planned.

5. Swagger server list hardcoded to localhost:4000 — trivial, fix before
   anyone tries to generate a third-party client SDK from the spec.

Exit criteria: idempotency middleware live on at least the
credential-issuance and tenant-creation routes; explicit written decision
on API keys (build or deprecate the UI) with an ApiKey model if "build";
Swagger servers list includes the real API host.
